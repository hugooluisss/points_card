# Hallazgos: Google Wallet

> Alcance documental: solo páginas oficiales de `developers.google.com/wallet` y páginas oficiales enlazadas desde ellas. Fecha de consulta para todos los hechos: 2026-10-11. Cada afirmación está marcada; **[SUPUESTO]** identifica lo no confirmado explícitamente en las fuentes consultadas y **[HIPOTESIS]** una conclusión razonada, no una garantía de Google.

## Tipos de pase para sellos, puntos y club

- [HECHO] `LoyaltyClass`/`LoyaltyObject` es el tipo diseñado para tarjetas de programas de lealtad; el objeto contiene datos por titular como `accountId`, `loyaltyPoints` y `secondaryLoyaltyPoints`. [Fuente](https://developers.google.com/wallet/retail/loyalty-cards), consulta: 2026-10-11.
- [HECHO] Loyalty puede mostrar saldo y etiqueta de puntos, un saldo secundario, nivel (`rewardsTier`), identificador de cuenta y código de barras; el formato predeterminado posiciona puntos y saldo en la tarjeta. El saldo debe caber en un campo corto (longitud recomendada de hasta 7 caracteres). [Referencia](https://developers.google.com/wallet/reference/rest/v1/loyaltyobject), [plantilla](https://developers.google.com/wallet/retail/loyalty-cards/resources/template), consulta: 2026-10-11.
- [HECHO] Loyalty admite `barcode` con tipo y valor; entre tipos oficiales están `QR_CODE`, `PDF_417`, `CODE_128`, `AZTEC` y `TEXT_ONLY`. Solo `QR_CODE` y `PDF_417` se identifican como compatibles con códigos rotativos; `TEXT_ONLY` no admite `alternateText`. [Barcode](https://developers.google.com/wallet/reference/rest/v1/Barcode), [tipos](https://developers.google.com/wallet/reference/rest/v1/BarcodeType), consulta: 2026-10-11.
- [HECHO] La referencia Loyalty no define un campo nativo de “sellos” ni una cuadrícula de progreso de sellos. [Referencia LoyaltyObject](https://developers.google.com/wallet/reference/rest/v1/loyaltyobject), consulta: 2026-10-11.
- [HIPOTESIS] Para un programa de sellos conviene modelar el progreso en Loyalty usando `loyaltyPoints.balance` (por ejemplo, “4/10”) o campos de texto personalizados y mantener el conteo autoritativo en el sistema del emisor; una representación visual tipo matriz de sellos sería contenido de imagen/módulo, no una función nativa confirmada. [Base para campos](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/pass-customization), consulta: 2026-10-11.
- [HECHO] `GenericClass`/`GenericObject` sirve para casos que no encajan en un tipo predefinido y permite campos de texto, imágenes, datos personalizados y código de barras, incluido QR. La documentación de Generic recomienda usar tipo Loyalty dedicado cuando el caso sí es una tarjeta de lealtad. [Generic overview](https://developers.google.com/wallet/generic), [referencia GenericObject](https://developers.google.com/wallet/reference/rest/v1/genericobject), consulta: 2026-10-11.
- [HIPOTESIS] Generic puede representar sellos como texto/imagen de progreso y un club sin puntos como credencial de membresía; Loyalty es la elección más directa si el club tiene puntos, saldo, identificador o niveles. Google no documenta una categoría independiente llamada “club”. [Base Generic](https://developers.google.com/wallet/generic), [base Loyalty](https://developers.google.com/wallet/retail/loyalty-cards), consulta: 2026-10-11.
- [HECHO] Un pase Generic tiene `barcode` con tipo/valor y módulos de texto, pero no los campos de saldo de Loyalty; puede organizarse mediante una plantilla de clase. [Referencia GenericObject](https://developers.google.com/wallet/reference/rest/v1/genericobject), [plantilla Generic](https://developers.google.com/wallet/generic/resources/template), consulta: 2026-10-11.
- [SUPUESTO] La documentación consultada no confirma un límite universal de campos de progreso ni promete que cualquier escáner físico procese cualquier simbología; se debe probar el valor y el tipo de código con los lectores del comercio.

## Emisor, demo y publicación

- [HECHO] Para emitir pases se necesita una cuenta Issuer de Google Wallet; para REST se debe habilitar Google Wallet API en Google Cloud y configurar autenticación. [Alta de Issuer](https://developers.google.com/wallet/generic/getting-started/issuer-onboarding), consulta: 2026-10-11.
- [HECHO] Las cuentas nuevas empiezan en Demo Mode: solo pueden guardar pases usuarios con roles Admin/Developer o cuentas de prueba registradas; los pases llevan `[TEST ONLY]`. [Demo y publicación](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/request-publishing-access), consulta: 2026-10-11.
- [HECHO] Para pedir acceso de publicación hay que completar Business Profile y crear al menos una Passes Class. La solicitud se envía desde Google Pay & Wallet Console y Google Wallet revisa la cuenta; el checklist recomienda crear también un objeto, probar integración/enlaces y esperar la aprobación antes de emitir en producción. [Solicitud](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/request-publishing-access), [checklist](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/launch-checklist), consulta: 2026-10-11.
- [HECHO] Una vez concedido el acceso, se elimina la etiqueta `[TEST ONLY]` y pueden emitirse pases en vivo. [Checklist](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/launch-checklist), consulta: 2026-10-11.
- [HECHO] Las clases deben ser aprobadas para poder referenciarlas desde objetos, según los esquemas de objetos de Wallet. [Referencia LoyaltyObject](https://developers.google.com/wallet/reference/rest/v1/loyaltyobject), consulta: 2026-10-11.
- [SUPUESTO] Las fuentes revisadas no publican un plazo fijo de revisión ni garantizan aprobación; el tiempo y resultado quedan a revisión de Google.

## Crear y actualizar después de que el usuario guardó el pase

- [HECHO] El pase se compone de una clase (propiedades comunes) y un objeto (datos particulares); para añadirlo se entrega al usuario un enlace o botón con un JWT firmado que incluye el objeto. [Flujo de emisión](https://developers.google.com/wallet/retail/loyalty-cards/overview/add-to-google-wallet-flow), consulta: 2026-10-11.
- [HECHO] La API REST ofrece `insert`, `get`, `list`, `patch` y `update` para objetos Loyalty; `patch` modifica campos parciales y `update` reemplaza el recurso completo. En `update`, los campos omitidos se borran; antes de hacerlo Google recomienda leer el recurso con `GET`. [Métodos](https://developers.google.com/wallet/reference/rest/v1/loyaltyobject), [guía de actualizaciones](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/updates), consulta: 2026-10-11.
- [HECHO] Cambiar la clase afecta a todos sus objetos; cambiar un objeto afecta solo ese pase. Los cambios de clase se reflejan en los pases asociados al sincronizar Wallet. [Guía](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/updates), [modelo clase/objeto](https://developers.google.com/wallet/generic/overview/how-classes-objects-work), consulta: 2026-10-11.
- [HECHO] Quitar el pase desde Wallet desvincula el objeto del usuario, pero no lo elimina del emisor; el usuario puede volver a guardarlo con el mismo objeto. [Clases y objetos](https://developers.google.com/wallet/generic/overview/how-classes-objects-work), consulta: 2026-10-11.
- [HECHO] El emisor puede añadir o cambiar mensajes y datos del objeto/clase con API después del guardado; una actualización no requiere crear y volver a emitir un objeto distinto. [Actualizaciones](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/updates), consulta: 2026-10-11.
- [SUPUESTO] Google no documenta en las páginas consultadas un tiempo máximo de propagación/sincronización para cada actualización.

## Mensajes y notificaciones

- [HECHO] **Mensaje del emisor con aviso:** `AddMessage` con `message_type: TEXT_AND_NOTIFY` añade texto a los detalles del pase y provoca una notificación de Wallet. El usuario debe tener habilitadas las notificaciones; los enlaces incluidos deben estar relacionados con el pase y respetar la Acceptable Use Policy. [Guía Loyalty](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), [tipo de mensaje](https://developers.google.com/wallet/reference/rest/v1/Message), consulta: 2026-10-11.
- [HECHO] El máximo documentado es 3 mensajes por pase en 24 horas que disparen notificación; excederlo puede dar `QuotaExceededException`, y Google puede limitar la cuota ante abuso/spam. El texto de notificación de bloqueo lo controla Google Wallet. [Guía Loyalty](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), consulta: 2026-10-11.
- [HECHO] **Aviso por cambio de campos:** usando `UPDATE`/`PATCH` y `notifyPreference: notifyOnUpdate`, Wallet puede notificar cambios a campos admitidos. Para Loyalty los campos documentados son `rewardsTier`, `secondaryRewardsTier`, `programName`, `loyaltyPoints.balance` y `secondaryLoyaltyPoints.balance`; también se limita a 3 actualizaciones notificables por pase en 24 horas. [Campos y cuotas](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), consulta: 2026-10-11.
- [HECHO] La restricción de que solo se envía actualización cuando faltan 3 horas o menos se aplica en la guía a cambios de hora de inicio de eventos/vuelos; no se presenta como regla general de Loyalty. `notifyPreference` es transitorio por solicitud. [Guía](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), consulta: 2026-10-11.
- [HECHO] **Notificaciones automáticas por vigencia:** Generic permite configurar aviso 24 horas antes del inicio del intervalo de vigencia y aviso de expiración 48 horas antes del final, mediante `upcomingNotification`/`expiryNotification`. Dependen de fechas y configuración del objeto. [Guía Generic](https://developers.google.com/wallet/generic/use-cases/notifications), consulta: 2026-10-11.
- [HECHO] **Avisos de proximidad (geográficos):** se agregan coordenadas en `merchantLocations` de clase u objeto; se admiten hasta 10 ubicaciones en cada nivel. El usuario necesita notificaciones y permiso de ubicación precisa siempre activa para Wallet. Google decide distancia, permanencia y texto; el aviso abre el pase y puede desaparecer al salir del lugar. [Guía de proximidad](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), consulta: 2026-10-11.
- [HECHO] Las notas de versión dicen que las notificaciones geográficas están disponibles para todos los tipos de pase regulares desde octubre de 2025. [Release notes](https://developers.google.com/wallet/docs/release-notes), consulta: 2026-10-11.
- [SUPUESTO] No se encontró en las páginas oficiales consultadas una lista de países admitidos para `merchantLocations`, ni cuota/frecuencia de avisos geográficos por persona o ubicación; no se debe prometer disponibilidad por país ni una frecuencia determinada.
- [HECHO] Las guías de notificación de Loyalty y Generic describen `TEXT_AND_NOTIFY` como mecanismo para ambos tipos; no requieren en esas páginas una aprobación separada específica de mensajería. Sí se requiere acceso de publicación para emitir a usuarios generales y cumplir AUP. [Loyalty](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications), [Generic](https://developers.google.com/wallet/generic/use-cases/trigger-push-notifications), [publicación](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/request-publishing-access), consulta: 2026-10-11.
- [HECHO] Para habilitar Smart Tap, Loyalty documenta requisitos de configuración como `enableSmartTap`, emisores de redención y valor de redención; el uso de terminal requiere configuración y certificación de Smart Tap. [Conceptos Loyalty](https://developers.google.com/wallet/retail/loyalty-cards/resources/terminology), [Smart Tap](https://developers.google.com/wallet/retail/loyalty-cards), consulta: 2026-10-11.
- [SUPUESTO] No se halló una aprobación adicional general requerida para mensajes `TEXT_AND_NOTIFY`, aparte del acceso normal de producción y políticas; la documentación sí establece límites, elegibilidad de dispositivo/usuario y control de entrega por Wallet.

## Costos

- [HECHO] El checklist oficial describe el paso a producción como emisión de pases live, pero las páginas consultadas no especifican tarifa de alta, emisión, almacenamiento o actualización de Google Wallet API. [Checklist](https://developers.google.com/wallet/retail/loyalty-cards/test-and-go-live/launch-checklist), consulta: 2026-10-11.
- [SUPUESTO] No se puede afirmar, con estas fuentes, que el servicio sea gratuito en todos los escenarios ni calcular costos indirectos del emisor (backend, SMS/email, POS, lector o proveedor de fidelidad); se debe confirmar cualquier cargo aplicable con las condiciones comerciales vigentes de Google y proveedores propios.
